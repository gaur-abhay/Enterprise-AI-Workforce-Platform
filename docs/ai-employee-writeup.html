The problem

A model that knows everything except your business

Ask a general-purpose AI what your travel policy allows, and it will answer confidently. It will also be making it up.

Everything an employee actually needs to know lives somewhere the model cannot reach: PDFs in a shared drive, policies in SharePoint, contracts in blob storage, figures in a database. A language model only knows what it was trained on, which produces four predictable failures — invented answers, information that went stale months ago, total blindness to anything company-specific, and no notion of who is allowed to see what.

Retrieval-augmented generation fixes the first three by finding the relevant material before the model writes a word. AI Employee is built on the more capable version of that idea: the system decides for itself what to look up and how, rather than following one hard-coded path.

Today

What it does right now

Point it at a folder or an Azure Blob container, run one command, and ask questions in plain English — from a terminal or over HTTP. What comes back is grounded in your documents, cites the document and page beside each claim, and says "I could not find anything about that" rather than filling the gap with something plausible.

The capabilities that are live

  • Natural-language Q&A grounded in indexed company documents, with an inline citation on every claim.
  • Two document sources behind one interface: a local directory, or an Azure Blob Storage container.
  • Incremental indexing — re-running over an unchanged container costs a single listing call and nothing else.
  • Multi-turn conversation, so follow-up questions keep their context.
  • A chat model and an embedding model chosen independently by configuration: Azure OpenAI, Google Gemini, or a fully local Ollama.
  • Every answer traceable end to end in the logs by a single correlation id.

How it works

Two pipelines, one index

Indexing happens offline and populates the store. Answering happens online and reads from it. Keeping them separate is what makes the system cheap to re-run and quick to answer.

Indexing — offline

  1. 01
    ReadA local folder or an Azure Blob container, authenticated by connection string or Entra ID.
  2. 02
    Skip what has not changedA two-stage check that avoids downloading, then avoids re-processing.
  3. 03
    Parse and splitPDF, Markdown and plain text, split into overlapping passages with page numbers preserved.
  4. 04
    EmbedBatched, and stamped with the exact model that produced each vector.
  5. 05
    StorePostgreSQL with PGVector, indexed for cosine similarity search.

Answering — online

A question arrives at the API. The agent decides whether it needs to search at all, forms its own query, reads what comes back, and either searches again with different wording or writes the answer. Nothing in the code makes that call — the reasoning loop does, which is precisely what allows it to recover from a bad first search.

Engineering

Six decisions that carry the system

Most RAG demos work on the happy path. These are the choices that decide whether it still works in month three, on someone else's data.

Decision 01 · Portability

No vendor is hard-wired

The chat model and the embedding model are selected separately by configuration. A client on Azure runs Azure OpenAI; a demo runs on a free Gemini key; a security-sensitive deployment runs embeddings locally through Ollama so document text never leaves the building. Provider SDKs load only when chosen, so a deployment installs what it uses.

Decision 02 · Correctness

Every vector remembers which model made it

Vectors from two different embedding models are not comparable — searching one with the other returns confident nonsense. It is a silent failure, and it is the one most likely to be introduced months later by someone changing a config value. Each stored passage records its model, and search only ever compares like with like. Change the model and the system returns nothing until you re-index, instead of returning something wrong.

Decision 03 · Cost

Re-indexing a large container is nearly free

Two independent checks, in order of cost. First the storage system's own change marker: if it matches what was indexed, the file is never downloaded. If it moved, the file is fetched and hashed — because a re-upload, a copy, or a metadata edit moves that marker without changing a single byte, and re-embedding a document that did not change is pure spend.

Document stateDownloadedRe-embedded
UnchangedNoNo
Touched, contents identicalYesNo
Genuinely editedYesYes
Deleted at source—Removed from the index
Decision 04 · Trust

Citations you can actually check

A citation that says policy.pdf proves nothing — three departments have a policy.pdf. Every passage returned carries the document's full location, its identity in the store, its page, when it was last indexed, and the passage text itself. A stale answer and a wrong answer look identical to a reader; the indexing timestamp is what separates them.

// one entry from the sources array on every answer

  "score":       0.747,
  "content":     "Employees receive a one-time stipend of…"
}
Decision 05 · Safety

Deleting from the index is opt-in and bounded

Removing documents that vanished from the source is necessary — otherwise the agent keeps citing a policy that was withdrawn. It is also the single most destructive operation in the system: a mistyped folder name or a credential that quietly lost its permissions produces an empty listing, and an empty listing naively means delete everything. So it never runs by default, it can only ever touch the exact scope that was just indexed, and an empty listing is refused by two independent guards.

Decision 06 · Accountability

Every answer is reconstructable

One correlation id is bound to each request and stamped on every line it produces — the model call, the searches, the database queries — and returned to the caller. A user reporting a bad answer can name the exact turn, and the log shows what was searched, what came back, and how it scored. In a regulated environment that trace is not a nice-to-have; it is the audit.

Known limits — deliberate, documented
  • Access control is not enforced yet. Document permissions are captured at ingestion and indexed, but retrieval does not filter on them, so every passage is currently visible to every caller. Acceptable while there is no authentication layer and no real multi-department content; it must close before there is. The fix is a filter clause, not a rebuild — which is exactly why the permissions were captured from day one.
  • No score threshold on retrieval. The obvious next guard, and deliberately absent: the cut-off cannot be chosen honestly without measurements from a real corpus. Set too high it silently returns nothing. That belongs after the evaluation harness, not before.
  • Conversations are held in memory. They do not survive a restart. Fine for a single-process build, replaced by a database-backed store before multi-worker deployment.
  • Scanned PDFs index as empty. There is no OCR stage yet, so an image-only PDF is reported as having no extractable text rather than silently indexing nothing.

Publishing this list is the point. A system that cannot tell you what it does not do yet is not one you should trust with your documents.

Run it

Four commands

The cheapest path needs one free Google API key and Docker. Nothing else.

# 1 · configure
cp .env.example .env

# 2 · install and start PostgreSQL with PGVector
make install && make up

# 3 · index whatever is in data/documents/ — or a blob container
make ingest
make ingest SOURCE=azure://corp-docs/policies

# 4 · ask
uv run python -m ai_employee.agent.runner "what is the home office stipend?"

Or run make api and post to /chat, which returns the answer, the passages behind it, the tool calls the agent made, and the correlation id for the turn.
